# SKYNET V0.9 — Product Convergence

V0.9 is the convergence release before SKYNET's first serious real-PC benchmark. The objective is not feature count; it is to close practical gaps that mature agent frameworks expose immediately in daily use.

## Targets

V0.9 attacks eight gaps:

1. deeper multi-agent orchestration;
2. more integrations without coupling the sovereign core;
3. durable sessions and searchable usage history;
4. better developer tooling;
5. practical browser/web use;
6. progressive, reusable skill learning;
7. channel infrastructure;
8. conversation-bound automations.

Trust & Resilience from V0.8 remains non-negotiable.

## 1. Multi-agent graph

The swarm is no longer a flat set of independent prompts. Tasks form a bounded DAG with explicit dependencies. Independent ready nodes run in parallel; downstream nodes receive previous specialist evidence.

Default topology:

```text
planner ─────────────┐
researcher ──────────┼─────────────┐
analyst ──────┬──────┘             │
              ├─ implementation ───┼─ critic ──┐
              └─ security ─────────┘           ├─ verifier
                                               │
                                         lead synthesis
```

Important trust boundary: swarm specialists reason but do not inherit the main agent's tool capabilities. Tool authority remains centralized in the governed ToolBus.

Every run can be persisted to `swarm-runs.db` for debugging and later evaluation.

## 2. Integration fabric

`IntegrationRegistry` records integration identity, kind, enabled state, capabilities, trust level and source.

It is declarative. A manifest cannot grant itself execution privileges.

Current built-in capability declarations include local inference, Windows, filesystem, PowerShell, browser, Git/developer tooling and channel infrastructure. MCP servers are discovered from the existing MCP configuration.

Configured MCP tools can be promoted into the model-facing tool schema as:

```text
mcp__server__tool
```

This improves practical tool discovery without bypassing governance. Every dynamic MCP action remains confirmation-required by default, risk-classified and receipted.

## 3. Sessions and history

`SessionStore` adds product-level session metadata on top of the existing message history:

- title;
- project;
- source channel;
- archive state;
- updated time;
- text search;
- fork.

Forking creates a new session with copied recent history so experiments can diverge safely.

The Desktop now exposes session switching, creation, forking and history search.

## 4. Skills

SKYNET keeps approved internal skills and inactive candidates, but V0.9 adds progressive disclosure:

```text
current request
   ↓
skill relevance search
   ↓
load only top relevant approved procedures
   ↓
execute + verify
   ↓
usage evidence
```

Optional external skill directories can expose `SKILL.md` content read-only. Presence is not trust: external procedures do not acquire executable authority or automatic promotion.

## 5. Browser/web harness

Two modes exist:

### HTTP read-only

Always available with the standard library. Supports absolute HTTP/HTTPS navigation, page text extraction and link discovery.

### Playwright local

Optional interactive Chromium installed through `install-browser.ps1`.

Interactive actions remain permission-gated. Playwright state is owned by one dedicated worker thread to avoid cross-thread browser failures when Desktop chat, automations and channels share the same Runtime.

## 6. Developer tooling

Bounded developer tools expose:

- environment doctor;
- project tree;
- source search;
- git status;
- git diff;
- recent commits;
- unit tests.

Read operations do not mutate the repository. Test execution runs local code and therefore requires confirmation.

The goal is not to expose an unrestricted second shell; PowerShell already exists behind its own higher-risk gate.

## 7. Channels

`ChannelHub` is a persistent channel-neutral inbox/outbox.

`skynet-channel` is an opt-in authenticated loopback HTTP bridge for adapter development. It does not pretend provider-specific Telegram, Discord, Slack or email adapters are already shipped.

Remote/channel prompts execute in their own bound session and cannot self-confirm consequential actions.

## 8. Automations

Routines now carry a `session_id`. This allows scheduled work to continue the correct conversation context.

V0.9 also supports:

- one-shot jobs;
- optional maximum run counts;
- automatic disabling after the run budget is exhausted.

The unattended permission doctrine is unchanged: a confirmation-required action becomes `needs_user`, never an automatic approval.

## Concurrency corrections

Productization exposed latent concurrency hazards that unit-only architecture work can miss. V0.9 makes the stores used by Desktop/automation/channel workers explicitly thread-safe:

- conversation memory;
- sessions;
- semantic memory;
- trajectories;
- channels;
- routines;
- checkpoints;
- skill usage;
- model telemetry/scorecards;
- signed receipts;
- swarm run traces;
- audit hash chain.

The Agent also serializes execution and provides `ask_in_session(...)` so parallel surfaces cannot corrupt the active conversation identity.

## Entry criteria for real-PC benchmark

Before benchmarking, CI must prove:

- package installs on Windows/Python 3.11;
- all legacy V0.1–V0.8 tests remain green;
- V0.9 sessions/history tests pass;
- channel/integration tests pass;
- external skill progressive-disclosure tests pass;
- automation migration/one-shot tests pass;
- multi-agent DAG validation tests pass;
- browser URL boundary tests pass;
- full Runtime smoke test passes without requiring Ollama;
- concurrent store/audit tests pass.

## Reality Benchmark — next phase

After installing V0.9 on the target PC, benchmark real tasks rather than architecture claims.

Primary metrics:

```text
Task Success Rate
Human Intervention Rate
False Success Rate
Recovery Rate
Average Steps
Average Latency
RAM / VRAM pressure
Permission Fatigue
Skill Reuse Rate
Browser Recovery Rate
Session Continuity Rate
```

Suggested benchmark families:

### Windows

- open Notepad, type and save;
- inspect an application via UI Automation;
- recover with vision when accessibility is insufficient;
- restart after a controlled failure and resume from checkpoint.

### Browser

- navigate and extract evidence;
- fill a form with explicit permission;
- recover from selector/navigation failure;
- verify the final page state rather than claiming success early.

### Developer

- inspect repository state;
- find the source of a failing test;
- patch only after approval;
- run tests and report exact evidence.

### Sessions/history

- recall work from an earlier session;
- fork an investigation and preserve the original;
- bind an automation to the correct project session.

### Skills

- solve a repeated workflow;
- generate/validate/promote a reusable skill;
- repeat the workflow and measure fewer steps/interventions.

### Multi-agent

- compare single-agent vs swarm quality/latency on architecture, debugging and security tasks;
- verify whether extra agents add measurable value instead of merely more tokens/latency.

## Benchmark philosophy

V0.9 does not claim SKYNET has already surpassed Ruflo, Hermes or OpenClaw. It creates a substantially fairer basis for that comparison.

The next release number should be earned by measured real-PC results, not by adding another feature list before field evidence exists.
