# SKYNET V0.3 — Checkpointed Local Autonomy

V0.3 moves SKYNET from an interactive local agent toward a persistent personal operating layer.

## New components

### ModelRouter
Routes each request among configured, installed Ollama models. The default model remains a guaranteed fallback. Routing is local and deterministic from task hints; no cloud broker is required.

### RoutineStore
SQLite-backed interval scheduler. Routines survive process restarts and track next run, last run and last status.

### CheckpointStore
Persists autonomy state before and after routine execution. A restarted routine can see the previous checkpoint but must verify current state rather than assuming the old state remains true.

### AutonomyRunner
Runs due routines. It deliberately refuses confirmation-gated tools in unattended mode. This creates an explicit `needs_user` state instead of granting the agent hidden privilege escalation.

### Skill candidate lifecycle
Learned procedures are written to `skill_candidates/` first. Validation requires purpose, preconditions, steps, verification and recovery sections and rejects explicit instructions to bypass permissions/audit controls. Valid candidates still require explicit promotion before entering the approved skill library.

### DesktopApp
A standard-library Tkinter desktop interface with chat, model/activity status, routine creation and automatic due-routine execution. Permission prompts are marshalled back onto the GUI thread.

### Runtime
CLI, desktop and worker now construct the same Runtime object. Memory, tools, routing, MCP, Windows control, routines and checkpoints therefore use one implementation and one policy surface.

## Trust boundary

Unattended autonomy is intentionally less privileged than an interactive session:

- observe/read tools: allowed according to policy;
- SAFE tools: allowed according to policy;
- CONFIRM tools: denied unattended;
- BLOCKED/unknown tools: denied always unless policy is explicitly changed by product code/user configuration.

## Failure/recovery behavior

A routine writes a `running` checkpoint before work begins. Completion produces `ok`, `needs_user` or `failed`. On a later execution, a non-success checkpoint is passed back only as contextual state; the agent is instructed to verify the current machine state before continuing.

## Next milestone

V0.4 should focus on product hardening rather than raw feature count:

- trusted-per-routine permission profiles;
- notification center for `needs_user` actions;
- model benchmarking and measured routing;
- richer desktop tray/background lifecycle;
- skill simulation/test harness before promotion;
- signed update channel, atomic upgrades and rollback;
- installer packaging for non-technical Windows users.
